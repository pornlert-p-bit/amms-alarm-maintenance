# รายงานผลทดสอบ — Login, สิทธิ์ตาม Role และ RLS

**วันที่ทดสอบ:** 26 กันยายน 2569
**สภาพแวดล้อม:** Next.js dev server บนเครื่อง (`localhost:3100`) ต่อกับ Supabase project จริง (`amms`, Singapore)
**ข้อมูลทดสอบ:** บัญชีทดสอบ 3 บัญชี (`admin@` / `tech@` / `viewer@amms-demo.test`) — ตาราง machines / alarms / maintenance_records ยังว่าง
**ผู้ทดสอบ:** ผู้พัฒนา (ผู้ใช้กรอกรหัสผ่านเอง) + Claude Code (ยิง API และตรวจผล)

## วิธีทดสอบ

1. Login ผ่านหน้าเว็บจริงทีละ Role
2. ตรวจหน้าจอ: เมนู, ป้ายสถานะ, การ redirect เมื่อเปิดหน้าที่ไม่มีสิทธิ์
3. **ยิง REST API ของ Supabase ตรง ๆ ด้วย session ของ Role นั้น** — ข้าม UI และ Server Action ทั้งหมด เพื่อพิสูจน์ว่าด่านสุดท้าย (RLS ในฐานข้อมูล) ปฏิเสธได้เองจริง ไม่ได้พึ่งการซ่อนปุ่ม
4. การทดสอบที่ต้องเขียนข้อมูลใช้ค่าที่ไม่มีผลเสียหาย (เช่นเปลี่ยน role เป็นค่าเดิม) และตรวจหลังทดสอบว่าไม่มีข้อมูลตกค้าง

> token ของ session ถูกใช้ภายในหน้าเว็บเท่านั้น ไม่ถูกแสดงบนจอหรือบันทึกลง log

## หมายเหตุ

1. **A5:** ตอนกด Back ชื่อแท็บแสดง "ภาพรวม" ชั่วครู่ก่อนเปลี่ยนเป็นหน้า Login — น่าจะเป็น cache ของเบราว์เซอร์ ผลสุดท้ายถูก redirect ถูกต้อง **ต้องทดสอบซ้ำบน Vercel (production)** เพราะการตั้งค่า cache ต่างจากโหมด dev
2. **ยังไม่ได้ทดสอบ** (รอ Module ที่เกี่ยวข้อง): การ UPDATE machines ด้วย technician เมื่อมีข้อมูลจริง, การอ่าน audit_logs ด้วย Role ที่ไม่ใช่ admin เมื่อมีข้อมูล (ตอนนี้ตารางว่างจึงสรุปผลไม่ได้), และ TC-NFR-03 (ปิด guard ใน Server Action แล้วต้องยังถูก RLS ปฏิเสธ) — จะทดสอบเมื่อมี Server Action ของ Machine
3. การทดสอบนี้ทำบนโหมด dev — จะทดสอบชุดย่อยซ้ำบน Vercel หลัง deploy
